# 一時チャットアプリ 要件定義書（Requirements）

- 版数: v1.2（2026-10-22 承認済み。v1.1→v1.2 でストレージ D2→D1・画像96KB/WebP を反映）
- 日付: 2026-10-22
- 開発手法: 要件定義 → 設計 → プログラミング → テスト の各工程を承認ゲート付きで進める
- 本ドキュメント: 要件定義工程の成果物

---

## 1. 概要

ブラウザ完結で一時的なメッセージのやりとりに利用できる、ルーム型のE2EEチャットアプリケーション。
アカウント登録・認証・認可は行わず、招待リンク（ルーム鍵）とPINのみで参加できる。
サーバ（Cloudflare）は暗号文とメタデータの中継・一時保管のみを行い、平文メッセージ内容・ルーム鍵・PINを知り得ない。

## 2. 用語の定義

| 用語 | 定義 |
| --- | --- |
| ホスト | 会話を一番最初に始める利用者。ルームを作成する |
| ゲスト | 会話に二人目以降に参加する利用者 |
| ルーム | メッセージの届く範囲。UUIDで識別される |
| `K_R` | ルーム共通鍵。32バイトの乱数。ホストが生成し、招待リンクのURLフラグメント経由でのみ配布され、サーバには絶対に送らない |
| PIN | ルーム参加用の6〜12桁の数字。ホストが決定し、リンクとは別経路で共有する。サーバにはハッシュのみ送信する |
| `H(・)` | SHA-256ハッシュ |
| 平文メタデータ | サーバが復号せず参照できるデータ（後述 FR-4.3, FR-5.2）。現時点で不可避なのは「メッセージのタイムスタンプ」と「メッセージ種別（text/image）」と「暗号文長」 |

## 3. 利用の流れ（基本シナリオ）

1. ホストがブラウザ上で表示名・ルーム鍵 `K_R`・PIN（自動生成6桁または手入力）を作成し、`H(K_R || PIN)` をサーバに送信してルーム作成を申請する。
2. サーバは `H(K_R || PIN)` を控えてから一意のルームID（UUID v4）を発行する。
3. クライアントは `<URL>/<ルームID>#<K_R>` を招待リンクとして生成し、クリップボードにコピーする。
4. ホストはゲストに招待リンク（および別経路でPIN）を送付する。
5. ゲストが招待リンクを開くと、フロントエンドがPIN入力を要求する（`#K_R` はサーバに送られない）。
6. PIN入力は招待時には毎回必須。サーバは `H(K_R || PIN)` を照合し、整合すれば参加を認める（セッショントークン等の発行はしない。以後の要求ごとに `H(K_R || PIN)` を提示し照合する）。
7. 参加後は同一ブラウザではPIN再入力を要求しない（PINはブラウザ内に保存）。
8. チャットはヘッダ部（表示名・タイムスタンプ等）とボディ部（メッセージ本文）からなるCBORを作成し、CBORメッセージ全体を暗号化してサーバに送信する。
9. 各クライアントはページの可視中に5秒間隔のポーリングで新着を取得し、ローカルで復号して表示する。ページ非表示・閉鎖中はWebプッシュ通知で着信を知る。
10. 過去メッセージはルーム参加時に、保持期間内のものでれば遡及取得して閲覧できる（後述 FR-5）。

## 4. 機能要件

### FR-1 ルーム作成（ホスト）

- FR-1.1 ルーム作成画面では、表示名（必須・1〜20文字）、`K_R`（32バイト乱数を自動生成、base64url表示）、PIN（6〜12桁の数字を自動生成、再生成・手入力可）を扱う。
- FR-1.2 `K_R` のエンコーディングは base64url（パディング無し）とし、招待リンクは `<URL>/<ルームID>#<base64url(K_R)>` の形式とする。URLフラグメントはブラウザからサーバへ送信されない。
- FR-1.3 サーバへのルーム作成リクエストは `H(K_R || PIN)` のみを含み、`K_R`・PIN・表示名を含めない。
- FR-1.4 `H(K_R || PIN)` の入力は `K_R` の32バイトにPINのUTF-8バイト列を連結した字节列のSHA-256と定義する。サーバは受信したハッシュを格納し、認証時に定数時間比較する。
- FR-1.5 ルーム作成成功後、ブラウザは `K_R`・PIN・表示名をローカル保存し、以後の入力を不要とする（同一ブラウザ・同一オリジンに限定）。

### FR-2 ルーム参加（ゲスト）

- FR-2.1 URLパスに有効なルームIDがある場合、参加画面に遷移し、URLフラグメントから `K_R` を復元する。フラグメント欠落時は参加できない。
- FR-2.2 PINを毎回入力させ、その場で `H(K_R || PIN)` を計算してサーバに照合を依頼する。一致すれば参加完了、不一致はエラー表示。
- FR-2.3 ルームIDが不正・消滅済みの場合はエラー表示。
- FR-2.4 参加完了時にブラウザ通知の許可を、ユーザ操作に応答して要求する（許可拒否時もアプリは動作する）。
- FR-2.5 ルームIDを知りかつ `H(K_R || PIN)` を知る者（同一鍵・PIN保持者）の複数同時参加を認める。なりすましの抑止は対象外。

### FR-3 メッセージング

- FR-3.1 表示名は1〜20文字。メッセージ本文は1〜400文字。
- FR-3.2 メッセージはCBOR形式で、ヘッダ部（メッセージUUID・種別 text/image・表示名・送信者タイムスタンプ・プロトコルバージョン）とボディ部（テキスト本文、または画像base64・ファイル名・MIMEタイプ）を持つ。
- FR-3.3 CBORメッセージ全体を暗号化する。サーバはヘッダ部の中身（表示名を含む）を一切参照できない。
- FR-3.4 サーバが平文で保持するメタデータは「送信者タイムスタンプ」「種別（text/image）」「暗号文長」「受信日時（内部管理用）」に限定する。種別は画像時の汎用通知のため平文が必須（FR-6.3）。
- FR-3.5 メッセージの並び順はクライアントの送信タイムスタンプのみで決定する。同一タイムスタンプの並び替えはサーバの受信順とする。送信側デバイスの時計ずれにより表示順が前後する可能性があることは許容する。
- FR-3.6 送信処理は冪等性を持たせないが、サーバが割り当てる行IDをクライアントへ返し、クライアントはこれにより同一メッセージの二重表示を排除する。ネットワークタイムアウト再送でサーバに重複格納された場合、送信側は2通分の表示を受容する。
- FR-3.7 メッセージ本文が400文字を超える送信はクライアントで弾き、サーバはサイズ上限超過を 413 で拒否する。
- FR-3.8 送信者が自分自身を含む全参加者として扱われ、送信者別のメッセージ履歴フィルタは持たない。

### FR-4 メッセージ取得（ポーリング）

- FR-4.1 ドキュメントが可視のとき、5秒間隔で最終既知メッセージ以降の差分をサーバから取得する。可視でなくなった時点でポーリングを停止し、復帰時に即時同期する。
- FR-4.2 取得した暗号文はローカルで復号し、IndexedDBに保存する。復号に失敗したメッセージはエラー表示とせず、ローカルにも保存しない。
- FR-4.3 取得要求は `H(K_R || PIN)` による照合を毎回伴う。サーバはルームの全メッセージを時系列で返すが、平文内容を知り得ない。

### FR-5 途中参加・履歴

- FR-5.1 ルーム参加時、サーバ保持内（7日間・後述 FR-8.1）の全メッセージを一括取得し、復号して表示する。
- FR-5.2 復号にはサーバが平文で持つ送信者タイムスタンプを用いる。復号失敗分は表示しない。

### FR-6 プッシュ通知

- FR-6.1 Service Worker と Web Push により、ページを閉じている間も着信を通知する。サブスクリプションはルームごとに登録し、プッシュ送信先としてサーバに保存する。
- FR-6.2 テキストメッセージは、暗号文全体（後述の上限以内）をプッシュペイロードに詰め、Service Worker がブラウザ内に保存済みの `K_R`・PIN・平文タイムスタンプから鍵を導出して復号し、送信者名と本文を通知に表示する。
- FR-6.3 画像メッセージ（暗号文が4KBを超える）は「📷 画像メッセージが届きました」の汎用通知とし、タップ後にブラウザ側で遅延取得する。
- FR-6.4 iOS Safari は「ホーム画面に追加」（PWAインストール）済みの場合のみ通知を受け取れる。このOS制約は要件として許容する。
- FR-6.5 通知タップでブラウザを前面化し、当該ルームを表示する。
- FR-6.6 プッシュ配信で 404/410 が返されたサブスクリプションはサーバから除去する。

### FR-7 ローカル永続化と閲覧

- FR-7.1 取得したメッセージ（テキスト・画像）および `K_R`・PIN・表示名・プッシュサブスクリプション情報は、IndexedDB に保存し、ブラウザを閉じても再閲覧可能とする。要件原文の「LocalStorage」はブラウザのローカル保存の意訳とし、5MB上限とbase64画像の非効率のため実方式は IndexedDB とする。
- FR-7.2 サーバから削除された後でも、ダウンロード済みのメッセージは閲覧できる。
- FR-7.3 明示的なローカルデータ消去機能は持たない（ブラウザのサイトデータ削除で消去可能）。
- FR-7.4 画像ファイルは base64エンコードした上で CBOR ボディに格納し送受信する。送信形式は WebP とする（入力として JPEG/PNG/WebP の変換を受け付ける。GIF・動画は対象外）。
- FR-7.5 画像はクライアント側で縮小・高圧縮し、**base64変換前のバイナリとして 96KB 以下**（長辺1280px以下、WebP）にしてから送信する。上限超過の画像はクライアント側でエラー表示。
- FR-7.6 ダークモードに対応する。初回は `prefers-color-scheme` を追従し、以後トグルで切り替え、選択はブラウザ内に保存する。

### FR-8 サーバ側自動削除

- FR-8.1 メッセージはサーバ受信から**7日間**を過ぎた時点でサーバから削除する。
- FR-8.2 ルームは最終メッセージから**30日間**メッセージが追加されない場合、ルーム定義・サブスクリプション・全メッセージを削除する。
- FR-8.3 D1 にTTL機構は存在しないため、削除は Cloudflare Cron Triggers（Scheduled Worker）で実装する（実行間隔は設計工程で確定。要件としては削除の最大遅延を1時間以内とする）。

### FR-9 ブラウザ対応とUI

- FR-9.1 モバイル（ファースト）とデスクトップのレスポンシブUIとする。スマホ向けの単独アプリや外部ブラウザアプリは提供しない。
- FR-9.2 対応ブラウザ: 最新2バージョンの Chrome / Firefox / Edge / Safari（デスクトップ）、Android Chrome、iOS Safari 16.4以上。IE、WebView組み込み環境は対象外。

## 5. セキュリティ・暗号仕様（要件として確定）

### SEC-1 暗号スイート

| 項目 | 仕様 |
| --- | --- |
| 認証付き対称暗号 | AES-256-GCM（改ざん検知を兼ねる） |
| 鍵導出 | HKDF-SHA-256: IKM=`K_R`(32B)、salt=PIN(UTF-8)、info=`"tempchat-msg-v1"` ‖ 送信者タイムスタンプ（ミリ秒10進文字列）、出力32バイト |
| IV | メッセージごとに12バイトの乱数を生成し、暗号文の先頭に連結して保存・配信する |
| ルーム認証ハッシュ | SHA-256(`K_R` ‖ PIN(UTF-8))。サーバは定数時間比較する |
| タイムスタンプ | 送信者デバイスの時刻（ミリ秒）。サーバは平文メタデータとして保持する |

### SEC-2 サーバが知り得る情報・知り得ない情報

- 知り得ない: メッセージ本文、画像、表示名、PIN平文、`K_R`
- 知り得る（不可避なメタデータ）: ルームID、ルーム認証ハッシュ、メッセージのタイムスタンプ、種別（text/image）、暗号文長、送受信時刻、プッシュエンドポイントURL

### SEC-3 免責事項（元要件より。本仕様でも変更しない）

1. 同一のルーム鍵とPINを持つものによるなりすましは防止しない。
2. ルームIDが漏れた際に暗号化されたメッセージ（暗号文）が漏洩することを許容し、認証・認可処理を実装しない。ルームIDのみの保持者には暗号文のみが渡り、復号は `K_R` と PIN を要する。
3. ルームIDが漏れた際に鍵を知らない第三者から無作為なメッセージが送信されることを許容し、CBORの形式チェックしか行わない（サーバのサイズ上限・種別検査のみ）。
4. PINに対するレート制限・施錠は行わない。`H(K_R || PIN)` はソルト無しの総当たりに対して露出していることを許容する（6桁以上の数字による実効的抑止に依存）。

## 7. 制約・前提

1. iOS Safari のWebプッシュはPWAインストールが必須（OS制約。FR-6.4）。
2. プッシュペイロード上限は約4KB。テキスト本文400文字＋CBOR＋暗号化で収まる前提。画像は載せられない（FR-6.3）。
3. `K_R` とPINが同一ブラウザ内に平文保存される（通知復号のため）。端末の紛失・マルウェア対策は対象外。
4. サーバは平文メタデータからメッセージの送受信時刻・頻度・種別の推移を観察し得る。メッセージ本文の秘匿は達成するが、トラフィック解析分析の秘匿は達成しない。
5. 複数タブ・複数ブラウザで同一ルームに同時参加できるが、既読・未読は同期しない。
6. Service Worker のキャッシュは静的リソースのみとし、暗号文のキャッシュは行わない。

## 8. 対象外（Out of Scope）

- アカウント・認証・認可・認可後の権限管理
- 電子署名・完全な本人確認・前向きの秘匿性（Forward Secrecy）
- 既成E2EEプロトコル（Signalプロトコル等）の採用
- オンライン状態表示、タイピングインジケータ、リーシート
- 単一メッセージの削除、ルームの手動閉鎖、ホスト退去
- 英語UI、多言語対応（日本語のみ）
- 音声・動画・ファイル一般の送受信（画像のみ）
- サーバ側レート制限・スパム対策（免責3に従う）
- ダウンロード・エクスポート機能、多端間同期
- ダークモード以外のテーマカスタマイズ

## 10. 受け入れ基準（テスト工程での検証項目と直結）

1. ルーム作成→UUID発行→招待リンク生成が完了する。
2. 誤PINによる参加は拒否される。正しいPINでは参加できる。
3. サーバD1を直接確認し、メッセージ平文・表示名・PIN平文・`K_R` が格納されていないことを確認する。
4. ホストとゲスト間で双方向のテキスト・画像メッセージが疎通し、本文は400文字まで、超過時はクライアントで送信できない。
5. 途中参加ゲストが保持期間内の過去メッセージを閲覧できる。
6. ブラウザを閉じた状態でテキストメッセージを送信すると、数秒以内にプッシュ通知（送信者名・本文付き）が到着する。画像メッセージは汎用通知になる。
7. 7日経過後のメッセージがサーバから消え、ローカルでは閲覧継続できる。
8. 最終メッセージから30日経過したルームが削除される。
9. ダークモードへの切替が機能し、設定が保存される。
10. 対応ブラウザ一覧（FR-9.2）で主要な閲覧・送信操作が可能である。
